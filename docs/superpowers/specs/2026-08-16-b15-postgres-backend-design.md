# B15: Postgres as a Configuration-Selectable Database Backend — Design

**Issue:** #56 (B15) · **Precedes:** B16 fly.io deployment (#57), which becomes
mostly stateless once a hosted database exists
**Phasing:** three PRs (owner-approved), one spec — see §Phasing

## Problem

The backend talks to SQLite directly: six raw-SQL stores (`users`,
`documents`, `folders`, `terminology`, `profiles`, `usage`) over the shared
`app/services/_sqlite.py` seam, ~95 statements total. A hosted deployment
(fly.io) with SQLite needs a volume, which pins the app to a single machine.
Supabase-hosted Postgres removes that constraint — but the stores assume
SQLite's dialect (qmark placeholders, `AUTOINCREMENT`, `lastrowid`,
`COLLATE NOCASE`, `PRAGMA table_info`) and, in one place, its single-writer
concurrency model.

## Decisions (owner-approved)

1. **Plain Postgres, orthogonal.** The backend treats the database as managed
   Postgres behind a DSN; any Postgres works, Supabase is the documented
   hosted instance. Database backend and `auth.mode` are independent — all
   four combinations are valid. RLS and realtime are out of scope: this app
   is the sole database client.
2. **Dual backend, thin dialect seam.** SQLite stays the default and fully
   supported. The existing hand-written SQL stays almost verbatim behind a
   small owned seam — no SQLAlchemy, no async store rewrite.
3. **Always-on CI coverage.** A Postgres lane runs on every backend PR via a
   GitHub Actions service container. The default local gate stays
   SQLite-only, Docker- and network-free.
4. **Import tool in scope.** A one-time SQLite→Postgres import ships as a
   `manage.py` subcommand.
5. **Sync stores, accepted latency residual.** Stores stay synchronous. CRUD
   routes are threadpooled `def` handlers already; store calls inside async
   handlers (auth, LLM gate) block the event loop for the duration of a
   pooled same-region query (~1–2 ms) in Postgres mode. Documented residual;
   `anyio.to_thread` is the follow-up lever if hosted latency proves worse.

## Requirements

### R1 — The `db` seam (`app/services/db/`)

`_sqlite.py` becomes a package: `__init__.py` (interface, factory, shared
errors), `sqlite.py`, `postgres.py`. `postgres.py` is imported only when
selected, so sqlite deployments never import psycopg.

The `Database` interface is exactly what stores use today:

- `connect()` — context manager yielding a connection; wraps a transaction
  (commit on success, rollback on exception) and releases the connection
  (close the SQLite connection / return to the psycopg pool) on exit.
- `raw_connect()` — the explicit commit/rollback variant that
  `UsageStore.reserve_llm_run` needs; caller closes/releases in `finally`.
- `dialect: Literal["sqlite", "postgres"]` — for the few genuinely
  dialect-specific branches (advisory lock, column introspection).

The yielded connection is a thin wrapper:

- `execute(sql, params)` translates qmark (`?`) placeholders to `%s` for
  psycopg. Safe because no store SQL contains a literal `?`; the seam's
  docstring records that invariant for future SQL.
- `executescript(ddl)` — SQLite native; on psycopg a plain `execute` of the
  multi-statement string.
- Rows behave like `sqlite3.Row` on both backends: mapping access
  (`row["email"]`) **and** positional access / tuple unpacking
  (`(spent,) = fetchone()`, `row[1]`). On psycopg this is a small custom
  row factory.
- One exception map: `sqlite3.IntegrityError` and
  `psycopg.errors.UniqueViolation` surface as a single seam-level
  `UniqueViolationError`. Store code catches only the seam error
  (`users.py` `create_user`/`link_external_id` are the current catch sites).
- `migrate_columns(conn, table, columns)` moves into the seam and goes
  dialect-aware: `PRAGMA table_info` on SQLite, `information_schema.columns`
  on Postgres. The three inline `PRAGMA table_info` uses in
  `documents.py`/`terminology.py`/`profiles.py` route through the same
  helper.

Stores change their constructor from `db_path: Path` to `db: Database` (plus
the existing optional busy `timeout`, which the SQLite implementation honors
and Postgres ignores in favor of the pool's checkout timeout). All six stores
share the one `Database` instance built in `main.py`; `manage.py` builds its
own via the same factory.

### R2 — Statement unification (both backends run the same SQL)

- `cursor.lastrowid` (5 sites: users, documents, folders, terminology,
  usage) → `INSERT … RETURNING id`. SQLite ≥ 3.35 supports `RETURNING`;
  Python 3.13 bundles ≥ 3.45.
- `INSERT OR IGNORE` (1 site: `profiles.py` seed markers) →
  `INSERT … ON CONFLICT DO NOTHING` (both dialects).
- DDL: one canonical schema string per store with a single per-dialect
  substitution for the auto-increment primary key —
  `INTEGER PRIMARY KEY AUTOINCREMENT` vs
  `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` (*by default*, so
  the import tool may insert explicit ids).
- Case-insensitivity: `COLLATE NOCASE` disappears from schema and queries —
  **everywhere**, not only email. `users.email` gets a unique index on
  `LOWER(email)`, lookups become `WHERE LOWER(email) = LOWER(?)`, listing
  becomes `ORDER BY LOWER(email)`. The per-owner/global name-uniqueness
  indexes in `folders.py`, `terminology.py`, and `profiles.py`
  (`… name COLLATE NOCASE`) become `LOWER(name)` expression indexes, and
  `ORDER BY name COLLATE NOCASE` becomes `ORDER BY LOWER(name)`; their
  duplicate pre-scan queries follow the same rewrite. On SQLite, `LOWER()` is ASCII-only — exactly
  NOCASE's semantics, so behavior is unchanged there. On Postgres, `LOWER()`
  folds full Unicode — a strict superset that matches `_throttle_key`'s
  `.lower()` normalization (`app/api/auth.py`) more closely than SQLite
  does. The `users.py` comment explaining the NOCASE/throttle-key alignment
  is updated to describe the LOWER() story. Existing SQLite databases keep
  the `COLLATE NOCASE` embedded in their `users` table definition
  (`CREATE TABLE IF NOT EXISTS` never alters an existing table); that is
  harmless — for ASCII input NOCASE and the new `LOWER(email)` unique index
  enforce the same constraint, and the old constraint simply becomes
  redundant.
- Types stay uniform across backends: TEXT ISO-8601 timestamps
  (lexicographic comparison, identical semantics), JSON as TEXT, booleans as
  INTEGER 0/1. No PG-idiomatic retyping.
- The partial unique index `idx_domains_global_name`
  (`terminology.py`) ports as-is — Postgres supports
  `CREATE UNIQUE INDEX IF NOT EXISTS … WHERE …`.

### R3 — Postgres implementation (`db/postgres.py`)

- `psycopg[binary]` + `psycopg_pool` as regular dependencies, imported only
  in this module.
- One `ConnectionPool` per `Database`, created at startup, closed on app
  shutdown (lifespan hook). Fixed defaults (min 1 / max 5, sensible checkout
  timeout); **no pool-sizing config knobs**.
- Schema initialization runs the same `CREATE TABLE IF NOT EXISTS` +
  `migrate_columns` path the SQLite stores run today, on first construction.
- Foreign keys: Postgres enforces them natively; the
  `PRAGMA foreign_keys = ON` call is SQLite-only in the seam.
- The DSN is used as given (tests append `options=-csearch_path%3D…` for
  schema isolation; no extra constructor parameters).

### R4 — `reserve_llm_run` concurrency (`usage.py`)

SQLite path unchanged (insert-first + single-writer lock, as documented in
the method). On Postgres, READ COMMITTED allows write skew: two concurrent
reservations each miss the other's uncommitted row and both pass the
budget/concurrency counts. Fix: in Postgres mode the reservation transaction
opens with `SELECT pg_advisory_xact_lock(<one constant key>)` — a single
global lock, not per-user, because the server-wide concurrency count spans
all users. This reproduces SQLite's global write serialization exactly, costs
nothing at reservation rate (one per LLM run), and releases automatically on
commit/rollback. The constant key is a named module-level constant with a
comment. `finish_run` and the sweeps are single-statement updates and need
nothing.

### R5 — Configuration

- New `database:` block in `Settings`
  (`app/core/config.py`): `backend: Literal["sqlite", "postgres"] =
  "sqlite"`, `extra="forbid"` like every other block. `db_path` stays
  top-level and keeps meaning "the SQLite file" (existing configs untouched).
- The DSN is a secret (contains the password): env-only `FW_DATABASE_URL`,
  never in config.yaml, never logged. Required iff `backend: postgres` —
  startup fails loudly when missing (same pattern as supabase auth mode's
  required env). Set while `backend: sqlite` → one startup warning naming
  the variable (name only, never the value), value ignored.
- `config.example.yaml` documents the block; no other knobs.

### R6 — Wiring

- `main.py`: build the `Database` once from settings, pass it to all six
  stores; close the pool in the lifespan shutdown.
- `manage.py`: builds its `Database` via the same factory from the same
  settings; the `_BUSY_TIMEOUT_SECONDS` semantics apply to SQLite only.
- Seed paths (`seed.py`, `seed_admin.py`, `seed_profiles.py`) call store
  methods only — unaffected beyond the constructor change at their call
  sites.

### R7 — Testing

- Default gate `uv run pytest -q` (from `backend/`): unchanged — SQLite,
  Docker- and network-free, green with zero warnings.
- Store-level test files (the 13 files constructing stores directly) get a
  backend-parametrized `db` fixture: `["sqlite", "postgres"]`. The postgres
  parameter skips unless `FW_TEST_DATABASE_URL` is set (skips are visible in
  the summary but keep the default gate green and warning-free).
- Postgres test isolation: each test runs in a throwaway schema — unique
  name, created by the fixture, selected via `search_path` in the DSN
  options, dropped in teardown. Tests never touch a live database
  (standing rule); `backend/data/fabulous.db` is never read or written.
- One PG-mode API smoke module: `create_app` with
  `database.backend=postgres` settings, exercising login, a CRUD round-trip
  (documents), and one metered check end-to-end. The full API test matrix
  deliberately stays SQLite-only.
- Concurrency regression test (real Postgres): concurrent
  `reserve_llm_run` calls from threads against one budget; asserts no
  overshoot. Mutation-verified: removing the advisory lock must make it
  fail (delete the guard, watch it fail, restore by re-editing — never
  `git checkout`).
- All new/changed guards mutation-verified per the standing rule.
- CI: new always-on job in `.github/workflows/backend.yml` with a
  `postgres:17` service container (matches the supabase stack's major
  version), exporting `FW_TEST_DATABASE_URL` and running the parametrized
  subset plus the smoke and concurrency modules.
- Local recipe (documented): `FW_TEST_DATABASE_URL` pointing at the supabase
  e2e stack's Postgres on port 54322 (stack managed exclusively via
  `supabase start`/`stop` / `scripts/e2e-supabase.sh`).

### R8 — Import tool (`manage.py`)

Subcommand `import-to-postgres`: reads a SQLite file (default: the
configured `db_path`), writes to `FW_DATABASE_URL`.

1. Refuses a non-empty target (any rows in any known table → error, no
   writes).
2. Pre-checks emails that are distinct in SQLite but collide under
   Postgres' full-Unicode `LOWER()` folding → error listing the affected
   row ids and emails. Printing emails is correct here: this is an
   operator-only CLI and the operator needs them to resolve the collision;
   the secret/token logging rules are about credentials, not account data.
3. Copies all tables in FK order with explicit ids, resets each identity
   sequence (`setval` to `MAX(id)`), verifies per-table row counts.
4. One transaction: all-or-nothing.

### R9 — Documentation

- New `docs/postgres-setup.md`: Supabase DSN guidance (direct connection or
  Supavisor **session** mode — required because the app pools connections
  itself and relies on advisory locks and `search_path`; transaction pooling
  breaks both), `FW_DATABASE_URL` setup, import-tool walkthrough, backup
  note ("your Postgres provider's backup story replaces copying the data
  directory").
- `docs/backend-architecture.md`: db-seam section (update per standing
  maintenance rule).
- `docs/supabase-auth-setup.md`: one cross-reference (auth mode and
  database backend are independent).

## Non-requirements

- No RLS, no realtime, no Supabase-specific database features.
- No async store rewrite; no `to_thread` wrapping in B15.
- No PG-idiomatic column retyping (BOOLEAN, TIMESTAMPTZ, JSONB).
- No pool-sizing or other new tuning knobs beyond `database.backend`.
- No frontend changes of any kind (backend-only milestone; no UI strings).
- No change to auth modes, throttles (in-memory), or the job store
  (in-memory).
- No live-Supabase tests; no change to the e2e suite's scope in this
  milestone.

## Phasing (three PRs, one branch each)

1. **PR1 — behavior-neutral prep on SQLite** (branch `b15-db-seam-prep`):
   seam package with the SQLite implementation only, store constructor
   change, `RETURNING`, `ON CONFLICT DO NOTHING`, the NOCASE→`LOWER()`
   migration of queries and indexes (email and name columns),
   `migrate_columns` relocation. No Postgres code, no
   new dependencies, no config change. The existing test suite pins
   behavioral equivalence; this PR carries the spec and plan documents.
2. **PR2 — Postgres backend** (branch `b15-postgres-backend`):
   `db/postgres.py`, dependencies, `database:` settings +
   `FW_DATABASE_URL`, advisory-lock fix, parametrized fixtures, smoke +
   concurrency modules, CI job.
3. **PR3 — import tool + docs** (branch `b15-postgres-import`):
   `import-to-postgres`, `docs/postgres-setup.md`, architecture-doc and
   cross-reference updates. Closes #56.

Each PR: Copilot review, every thread replied to and resolved, LOGBOOK entry
as last commit, owner merges. Only PR3's body carries `Closes #56.`

## Global constraints (binding, unchanged)

- Live DB `backend/data/fabulous.db` never touched by tests; `tmp_path`
  (or throwaway-schema Postgres) settings everywhere.
- `uv run pytest -q` (from `backend/`) green with zero warnings, Docker- and
  network-free; frontend gates untouched (no frontend changes).
- Single-file pytest runs use `-n0`; never `-p no:xdist`.
- Secrets from env only; `FW_DATABASE_URL` name may appear in output, its
  value never; token values never logged.
- No public self-signup; `require_admin` stays on the admin router; XSS
  rules unchanged (no frontend changes anyway).
- Never force-push, amend, or rebase published history; branch + PR; owner
  merges (rebase-merge).
- Commit trailers per repo convention on every commit.
